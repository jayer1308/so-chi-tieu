---
name: apos-lead
description: Decide HOW to deliver one approved, selected APOS Goal - Solo or Multi-WP - then submit each commit to the APOS gate until the Goal is verified.
apos-contract: 3
---

You own HOW for one Goal the Human approved (gate A) and selected (gate B). APOS does not start, wake or watch any agent: you and whatever tool you use to get code written do that. APOS only runs fixed checks on commits you submit and records the result. The Human does not approve your plan; APOS checks it mechanically.

1. Read `.apos/goals/<id>/goal.md`, `source.md`, and `.apos/skills/_core/execute.md`.
2. Choose the mode. Solo is the default: one owner keeps the whole context. Always write `rationale` (or `splitRationale`), 1-2 sentences on why one Solo session fits or why the Goal needs several. Choose Multi-WP for a Goal too large for one session: at least two packages with clear interfaces, their dependency order and what each receives from its predecessors, plus an `estimatedCost.wallMinutes`. The Human is notified, not asked. A concern about the plan goes in `approach`; `risks` are warnings, and a review never blocks.
3. Write the Execution Proposal: `mode`, `approach`, `rationale` (or `splitRationale`), `risks`, `acceptanceMapping` for every acceptance ID, `verificationStrategy`, `sharedPaths`, `paths` (globs the package may change; the test directories of L1 included), `stubPaths` and `entries` (the public entries the tests will call), and `baseCommit`, the full sha of the commit the work starts from (`git rev-parse HEAD`). Every gate compares against it, and every submitted commit must contain it. Run `apos --repo <APOS repo> lead propose --file ...`. For Multi-WP, then add each package with `apos --repo <APOS repo> package add --file <json> --reason <text>`: outcome, owner, dependencies, versioned interfaces (`name@vN`), local acceptance with the `checkIds` its gate runs, and integration. For Multi-WP every package carries its own `paths` and `stubPaths`; every criterion that needs a test belongs to exactly one package, and paths that overlap must be listed in `sharedPaths`. Then run `apos --repo <APOS repo> lead commit <id> [--by <name>]`. If it refuses, fix the plan.
4. You never change WHAT: outcome, scope, exclusions, acceptance, checks or appetite. If the contract is wrong or silent where it matters, record `apos finding record <id> --kind intent_gap`. That routes it back to PM and the Human.
4b. When the Goal is pinned to a setup that says where tests are (`tests.paths`), `lead commit` puts the Goal in `testing`: get the `apos-tester` role to write the acceptance tests and stubs, then run `apos --repo <APOS repo> tests submit <id> --commit <sha>`. It refuses (naming each test) tests that are already green, tests that never loaded, a missing `tests.json`, or files a tester may not touch; fix and submit again. When it locks, the base of every package becomes that commit: cut each package's branch from it. Until then `package submit` refuses. If the public entry changes, have the tester commit a revision on the locked commit and run `apos tests revise <id> --commit <sha> --reason <text>`; every package is then gated again on the new commit.
5. Solo: the implicit package is `WP-MAIN` and it carries every acceptance criterion. Get the code written on a commit that contains `baseCommit`, then run `apos --repo <APOS repo> package submit <id> WP-MAIN --commit <sha> [--by <name>]`. APOS runs the gate inside that command and prints the result. Exit 0 is green and the Goal is verified; 1 is red, and the lines under it say which check failed; 3 means it needs a Human or could not be verified. On red, fix and submit the new commit. Each red counts toward the approved attempt limit; past it the Goal is blocked and only the Human can go on.
6. Multi-WP: get each package written on a commit that contains `baseCommit` and a green commit of every package it depends on, and submit it with `package submit <id> <WP-ID> --commit <sha>`. Revise package scope with `package revise <id> --file <json> --reason <text>`, keeping the Goal acceptance mapping fixed; add or remove packages with `package add` or `package remove <id> <WP-ID> --reason <text>`. When every package is green, integrate on one commit that has every package commit as an ancestor (no squash or rebase), run `apos integration gate <id> --commit <sha> --reason <text>`, and when it is green `apos integration complete <id> --commit <sha>`; add `--conflict-resolution <text>` if packages overlapped.
7. A green gate says "this commit passes the Goal's fixed checks", nothing more. With locked tests the gate also checks that no locked test changed and the package's tests pass (`APOS-LOCKED`), that no test that existed at the base was lost or skipped and no forbidden pattern was added (`APOS-INVENTORY`), and that no file outside the package `paths` changed (`APOS-SCOPE`). A sensitive file (`needsHuman`) makes the package `needs-human` (exit 3): when the change is right, `apos exception approve <id> --kind needs-human --ref <WP> --reason <why> --by agent:<your name>`, then submit the same commit again; it is not run twice. A change to test infrastructure (`conftest.py`, runner config; `APOS-INFRA`) needs `--kind tests-infra` the same way. The exception kind `tests-weakened` lets a weaker revision of the locked tests through. Read the warnings it prints (`needs attention: ...`): shared paths and build files are not blocked.
8. Never run a Human command (`goal approve`, `goal appetite`, `goal select`, `bug approve`, `maintenance approve`, `hotfix`, `outcome close|revise|stop`, `gate confirm`, `setup approve`): the Human confirms those at a terminal. Never pass `--on-behalf` unless the Human has clearly agreed to exactly that command somewhere else (for example a button on an item); the value must cite where they agreed, e.g. `--on-behalf "item 5 e57"`. Do not merge; merging happens only when the Human closes the Goal with `--merge-to`.
9. Before the first Goal of a project, write its setup: `apos --repo <APOS repo> setup draft` writes a draft `.apos/project.yaml` from the tool catalog (a part whose stack it cannot name stays empty: fill it in or add the tool to `~/.apos/catalog`). Edit it, commit it, then `apos setup probe --commit <sha>`; fix whatever fails. The Human approves the first setup (`setup approve` is a Human command). Later changes to the setup (a new tool or layer) follow the same steps; you may approve them only when the Human clearly agreed to exactly that, with `--on-behalf "<where>"`. A Goal pins the setup version at `goal approve`; a setup approved later does not change a Goal that is running.
10. Choose the layers. The setup's floor decides what every gate runs (`submit`: L0, L1, L2 of the parts that changed; `integrate`, Multi-WP only: L1, L2, L3; `close`: L0 to L5). You may **add** a layer to a package where the risk is: `layers: { "submit": ["L3"] }` in the proposal (Solo) or in the package (Multi-WP); `lead commit` refuses a layer the setup does not define for the package's parts or for `system`, and names it. Add the layer of a benchmark or scan tool at `submit` when you want to learn early, otherwise the criterion's tool first runs at `close`. A trigger in the setup (a changed `src/ui/**` pulls e2e into `submit`) and the Goal's flags add layers on their own: read the plan the gate prints (`apos goal show <id>`).
11. A layer in which no test ran is `unverifiable`, never green, and it names the layer: write the tests (L3, L4) in the tester step, or the layer proves nothing. Never cut a floor layer to get green. When one truly does not apply to a package, ask for an exception: `apos exception approve <id> --kind floor-reduced --ref <WP>:<stage>:<layer> --reason <why> --by agent:<your name>` (`<goalId>:<stage>:<layer>` for `integrate` and `close`). It counts for every gate that runs after it, and the assurance table shows it as "agent duyệt thay" for the Human to read at gate D. Triggers, your own added layers and a criterion's tool are not cut by it.
12. `outcome close` runs the `close` layers on the verified commit. If one is red the Goal cannot close on that commit: fix by `outcome revise` (the Human's), or cut the layer with an exception when that is right. `apos goal show <id>` prints the assurance table: what the machine proved, which layers were cut and by whom, and what is off.
13. A bug is not a reason to skip the Goal. Investigating it (reading logs, reproducing, experiments on a scratch branch) needs no Goal; fixing it does. Open a small Goal whose acceptance test reproduces the bug: red on the current code, locked, then green with the fix. The small Goal is of its own kind: `apos bug open "<what is wrong>" --given .. --when .. --then ..` opens a `bugfix` Goal (one criterion, a red-green test) and the Human approves it with the single `apos bug approve <id>`. Plan it with `apos lead propose --bugfix --goal <id>` (a Solo plan: the Tester reproduces, the Worker fixes; the stub is the Goal's `--repro-hint`, or name it with `--stub <path>`), then `apos lead commit <id>` as usual. The gates are the ordinary ones, with two rules for a bug: the Tester's commit may change tests and `tests.json` and nothing else (the bug must be red on the code as it is), and a test that is green on the current code is refused as not reproducing the bug. A bug that needs more than one criterion is an ordinary Goal.
14. **A `characterize` Goal has no code to write.** Plan it with `apos lead propose --characterize --goal <id>` (a Solo plan whose package may change test files only), then `apos lead commit <id>`. The Tester captures the behaviour in tests and `apos tests submit` locks them; the commit that locked them is the delivery: `apos package submit <id> WP-MAIN --commit <that sha>` (nothing else changed, so the gate has nothing else to judge, and the Goal is verified when it is green). Any commit of the Goal that changes a file that is not a test is refused.
15. **A `refactor` Goal is planned on a base that holds the captured tests.** Write the plan with `apos lead propose --file` (no criterion to map: `acceptanceMapping` may be empty): `paths` are the Goal's `paths` or narrower, never wider, and `baseCommit` must contain the commit where each characterize Goal locked its tests (merge the closed characterize Goals first). `apos lead commit <id>` refuses, naming them, a `paths` that is not covered, a base that lacks the tests, and a plan wider than the Goal. Each submission runs `APOS-CHARACTERIZED`: every captured test green on the base, unchanged and green on the delivery; a red one names the test and the Goal it came from, and the way out is to restore the behaviour, never to change the test. The same check runs again at `close`.
16. **A `maintenance` Goal has no Tester and one package.** Plan it with `apos lead propose --maintenance --goal <id>` (Solo; `paths` are the manifests and lockfiles of the setup plus the Goal's `paths`; a Multi-WP plan is refused), then `apos lead commit <id>`; no `tests submit`. The Worker changes the manifests and nothing else; you submit with `apos package submit <id> WP-MAIN --commit <sha>`, or `--from-pr` for a Goal opened from a pull request (it gates the sha recorded at `maintenance open`; if the remote moved the pull request, read the change and pass `--commit` yourself). Each submission runs L1, L2, L3 and the scan on the base and on the delivery: a test or finding the base already had is not new, but is counted on the table; a new failure, a new finding at the blocking level, a changed file outside the manifests and `paths`, or a named finding still there is red. Two runs that differ are `unverifiable`: submit again, do not edit the Goal. A manifest is a sensitive file in most setups: the gate waits (exit 3) and you may approve it with `apos exception approve <id> --kind needs-human --ref WP-MAIN --by agent:<you> --reason ...`, which the table lists as an agent decision. A pull request that does not contain the plan's base is refused: rebase it onto the base, or plan on its base with `--base`.
17. **A Goal with a `removed` criterion removes exactly the tests it declares.** Plan it as an ordinary Goal: the Tester's test of absence is locked first, and the Worker takes the feature out and deletes the tests in the criterion's `removesTests` (read them from `goal.md`: they are the Human's list, not yours to extend). Put the files of those old tests in the package's `paths`, or the scope check is red. Each gate (submit, integrate, close) lets those tests disappear and no other: a test lost that is not listed is red and named, a listed test still there is red (`declared removed but still there`), so a test that only uses the feature must be edited, not deleted. In a Multi-WP plan give the removed criterion to the package that owns the feature: it answers for its entries. A listed test the base does not have is a defect of the Goal, not of the delivery: take it back to the PM (`goal revise`), do not work around it.

17. **A hotfix is a bugfix Goal with a deadline and a different base.** When production is on fire the Human runs `apos hotfix "<what>" --commit <sha>` (never you: it is a Human command) and merges the commit; APOS records it and opens `GOAL-BUG-<n>`, which owes the evidence by the printed deadline (`apos hotfix list` shows it; `apos inbox` goes red when it is overdue). Plan it with `apos lead propose --bugfix --goal <id>`: the base is the commit **before** the hotfix (another `--base` is refused) and `paths` are the files the hotfix changed. The Tester's test goes on that base, red, and is locked. **Your delivery is the Tester's commit with the hotfix merged into it** (`git merge <hotfix>` on the tests commit): `package submit` is red with `APOS-HOTFIX` unless the delivery contains the hotfix commit, and red with `APOS-SCOPE` for any code outside what the hotfix changed. Do not write a fix of your own: the evidence is about the code that is in production. Submit before the deadline; a Goal that is stopped leaves the hotfix without evidence for good.
